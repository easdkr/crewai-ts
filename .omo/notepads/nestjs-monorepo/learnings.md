## Task 7 (NestJS CrewModule.forRoot({ llm, memory, knowledge })) — 2026-06-08

**Gotchas**

- **The plan's `crew-module.ts` snippet uses `require("@crewai-ts/core")` inside the `useFactory`** (not `import`). This is intentional: `crew-module.ts` sits in `packages/nestjs/`, which `peerDepends` on `@crewai-ts/core`. A static `import { Crew, Process } from "@crewai-ts/core"` at the top of the module file is fine for tsc type checking (it only needs the types), but the runtime factory defers the `require` so the `dist/index.js` doesn't eagerly resolve core at module-load time. With the static import the nestjs dist would also need core to be installed at runtime; the `require` form keeps the lazy-load contract that NestJS factories are designed for. I followed the plan verbatim. The `as typeof import("@crewai-ts/core")` cast on the `require` result is needed because `require` returns `any` by default — without the cast tsc can't verify that `Crew` and `Process` are present on the namespace.

- **`@crewai-ts/core` exports BOTH a value named `Crew` and a value named `Process` (the enum)**. Both come through cleanly with `const { Crew, Process } = require("@crewai-ts/core")`. The `Process.sequential` enum value resolves to the string `"sequential"`, which is the value `Crew` expects in its `process` option. No renames or aliases needed.

- **The `@Module({})` decorator on `CrewModule` is required** even though the decorator config is empty. Without it, NestJS's `Test.createTestingModule({ imports: [CrewModule.forRoot(...)] })` may or may not work depending on Nest version — but more importantly, the `.d.ts` would be missing the decorator metadata and the class would look like a plain class. The plan's spec explicitly calls out `@Module({})` (not omitting it) — followed.

- **The `forRoot()` no-args guard** uses `if (!options || !("llm" in options))` to handle THREE failure modes in one check: (a) `forRoot()` with `undefined`, (b) `forRoot(null)`, (c) `forRoot({})` (missing `llm` key). The `'llm' in options` test is the right one for case (c) — it would NOT throw for `{ llm: null }` or `{ llm: undefined }` because those keys ARE present, just falsy. The plan's contract is that forRoot requires at least `{ llm }` to be PRESENT (not non-nullish). This matches NestJS's typical `forRoot` pattern.

- **The test "forRoot without arguments errors" uses `@ts-expect-error`** for the `CrewModule.forRoot()` call — this is required because `CrewModuleOptions.llm: LLMSupply` makes `llm` a required property (not optional in the type, even though `LLMSupply` itself includes `null | undefined`). Without `@ts-expect-error` the test file won't compile. The runtime assertion `expect(() => CrewModule.forRoot()).toThrow(/llm is required|CrewModule\.forRoot/)` is a regex so it works with both the spec's error message ("CrewModule.forRoot requires at least { llm }") and any future tweak.

- **`moduleRef.get(LLM)` returns the EXACT reference** for object/function values (not a copy). This is the NestJS DI contract — `useValue: options.llm` stores the reference and `get(token)` retrieves it. The test `expect(moduleRef.get(LLM)).toBe(mockLlm)` (with `toBe`, not `toEqual`) verifies reference identity, not structural equality. For `null`/`undefined` values, `toBeNull()` is the right check.

- **`useValue: options.memory ?? null` (and same for knowledge)** — when the user omits `memory` or `knowledge`, the provider stores `null`, NOT `undefined`. ## Task 8 (NestJS CrewModule.forRootAsync({ useFactory, inject, imports })) — 2026-06-08

**Gotchas**

- **The `forRootAsync` `useFactory` MUST be defined for the runtime guard to work.** The interface marks `useFactory` as required (not `?:`), but the runtime guard `if (!options?.useFactory)` covers three call sites: `forRootAsync()` (no args → `options` is undefined), `forRootAsync({})` (empty object → `useFactory` is undefined), and any future call with a falsy `useFactory`. The two RED tests (4 and 5) test the SAME code path (`forRootAsync({})`) — test 5 is a copy of test 4 to match the plan's "or useClass" framing even though `useClass` is explicitly out of scope. The `@ts-expect-error` directive in both tests is required because `CrewModuleAsyncOptions.useFactory` is required; without it tsc would fail the test file at compile time.

- **The `CREW_MODULE_OPTIONS` string token (not a symbol) is intentional** — using a string token is the canonical NestJS pattern for internal/private providers that don't need to be exposed to consumers. Symbols (`Symbol.for(...)`) leak into the global registry, and exporting `Symbol.for("crewai-ts/CREW_MODULE_OPTIONS")` from `@crewai-ts/nestjs` would just be ceremony for an internal-only token. The 4 token providers (`LLM`, `MEMORY`, `KNOWLEDGE`, `CREW_FACTORY`) all `inject: ["CREW_MODULE_OPTIONS"]` — NestJS resolves the string token to the factory provider and passes the result to each `useFactory`. The `CREW_FACTORY` provider in the async path is the same `useExisting: DefaultCrewFactory` pattern as `forRoot` — same instance, just registered again in this module's `providers` array.

- **The `imports` field uses a `readonly` array on the public type but a mutable spread on the output.** `CrewModuleAsyncOptions.imports: readonly (DynamicModule | Type | ForwardReference)[]` is `readonly` to prevent the caller from mutating it after the fact, but the implementation does `imports: [...(options.imports ?? [])]` to satisfy NestJS's expected mutable `DynamicModule.imports` type. The spread is O(1) for the empty case and O(n) for the non-empty case; not a performance concern. Same pattern for `inject: [...(options.inject ?? [])]`.

- **`@Module({})` on `CrewModule` is critical for `forRootAsync` even though it has no providers/exports of its own** — the returned `DynamicModule` references `module: CrewModule`, and NestJS's testing module compiles the module class to wire up the providers. If `@Module({})` were omitted, the dist would compile but `Test.createTestingModule({ imports: [CrewModule.forRootAsync(...)] })` would throw `Nest cannot create the module instance` because NestJS wouldn't recognize `CrewModule` as a module. The Task 7 gotcha covers this; the same constraint applies to the async path.

- **The async providers use the `string` token `"CREW_MODULE_OPTIONS"` in BOTH the factory provider's `provide` AND the consumer providers' `inject`.** This is the standard NestJS pattern (see https://docs.nestjs.com/fundamentals/async-providers). The `string` form is fine because the token is private to this module — it's never re-exported from `src/index.ts`, and external consumers never need to `inject` it. The `useFactory: (opts: CrewModuleOptions) => opts.X` cast tells tsc that the injected value matches the `CrewModuleOptions` shape, but at runtime NestJS doesn't enforce the type (it just passes the factory's return value through).

- **`as const` and `readonly` arrays in tests don't matter for vitest's runtime behavior** — the `readonly` qualifier is a tsc-level type check only, erased at runtime. The new `crew-module-async.test.ts` test #1 returns an async function as the LLM (`asyncLlm: () => Promise<string>`), which at runtime is just a function reference. NestJS's `useFactory: (opts) => opts.llm` returns it verbatim, and `moduleRef.get(LLM)` returns the same reference. The `expect(moduleRef.get(LLM)).toBe(asyncLlm)` uses `toBe` (not `toEqual`) to assert reference identity.

- **Test #2 ("injects other providers") demonstrates the canonical cross-module DI pattern.** A custom `ConfigModule` provides a `CONFIG` string token; the test calls `forRootAsync({ imports: [ConfigModule], inject: [CONFIG], useFactory: (config) => ({ llm: config.defaultLlm, ... }) })`. - **The `inject` parameter's type union includes `string | symbol | Type | (abstract new (...args: never[]) => unknown)`.** This matches NestJS's `FactoryProvider['inject']` type, which is intentionally permissive (it accepts any of: a string token, a symbol token, a class type, or an abstract class). ## F2 fix: relax `LLMSupply` / `KnowledgeSupply` / `useFactory` (Task 16)

- **`pnpm -F @crewai-ts/nestjs check` (tsc --noEmit) is the gate that catches test-file type errors.** `pnpm -F @crewai-ts/nestjs build` (tsup + `tsc -p tsconfig.build.json`) only checks `src/` and reports success even when test files are broken. The two commands are NOT equivalent — `check` is the canary for test type regressions, `build` only covers production code.

- **`LLMFunction` from core is `(messages, options?) => MaybePromise<LLMResponse>` with NO optional parameters and NO zero-arg overload.** A test's `(): string => "mock-output"` is structurally incompatible with `LLMFunction` because (a) the test function requires zero parameters while `LLMFunction` requires `messages`, and (b) TypeScript's parameter bivariance / strict function types reject zero-arg functions as assignable to a function that expects arguments. The runtime Agent accepts the mock because the call site duck-types the function (it just invokes `llm(messages)` and treats the return as `LLMResponse = string | ToolCalling`), but TypeScript can't prove this.

- **`Knowledge` from core is a class with 14+ properties (`sources`, `collectionName`, `collection_name`, `storage`, ...).** A plain `{ id, content }` object is not assignable to it. Tests want to pass plain objects (or `as const` arrays) as mocks. The fix widens the supply type to `readonly unknown[]` — the actual `Knowledge` class still works (it's a structural supertype via covariance), and mocks also work.

- **The permissive `(...args: never[]) => unknown` pattern is the standard TS escape hatch for "any function".** `never[]` makes the function parameters bottom-typed, so every function type is assignable (function parameter types are contravariant, but `never` is the bottom of the type lattice so anything flows in). This preserves the "rejects non-functions" guard (`number`, `boolean`, etc. still fail) while accepting `() => string`, `(messages) => Promise<LLMResponse>`, async functions, etc.

- **`useFactory` had to be widened from `(...args: unknown[]) => ...` to `(...args: any[]) => ...`.** With `unknown[]`, a typed factory like `(config: { defaultLlm: () => string }): CrewModuleOptions => ...` is rejected because `unknown` is not assignable to `{ defaultLlm: () => string }`. With `any[]`, the inner parameter types flow through unchanged. This is the same pattern NestJS itself uses internally for `FactoryProvider['useFactory']`. The `any[]` is scoped to the parameter list (a bivariant slot) — return type stays strict.

- **The docstring on the relaxed types is load-bearing.** A drive-by "this should just be `LLMType`" cleanup would re-introduce the F2 failures and pass `check` for `src/` only. The comment explicitly records (a) why we diverge from the core's stricter types, (b) how to narrow back with `satisfies LLMType` when strict typing is needed, and (c) the runtime contract that justifies the permissiveness. Keep it.
